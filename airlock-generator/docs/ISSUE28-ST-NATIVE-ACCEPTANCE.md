# Issue #28 — ST: порядок нативной приёмки

Ветка `codex/airlock-28-st-native-acceptance`, исходная точка `6dc6481`.
Подготовка начата 21.10.2026. Текущий результат и ограничения записаны в
[ISSUE28-ST-STATUS-2026-10-21.md](ISSUE28-ST-STATUS-2026-10-21.md).

Исходники находятся в `experimental/issue28/st-acceptance/`:

- `FB_ST_TimerProbe.st` — этап 0, один SYS.TON 10 s и диагностика свежего фронта.
- `FB_Airlock2.st` — этап A, один двухдверный автомат.
- `immutable-inputs.json` — SHA256 прежних OWLE и неизменяемого эталона PR #30.

Файлы `.st` — исходники для редактора Owen Logic. Они не являются готовыми
`.fbst` или `.owle`. Не переименовывать расширение и не добавлять выдуманную
структуру ZIP. Нужны настоящий GUI Save As и экспорт блока из редактора.

## Этап 0: подтвердить синтаксис и таймер в Owen Logic

1. На HOME-PC открыть отдельный процесс Owen Logic. Не закрывать и не менять
   ранее открытые проекты. Создать **новый** проект ПР102 без поиска прибора.
   ПР100 допустим только при подтверждённой модификации М02.
2. Кнопка «Создать функциональный блок на ST». Вставить **весь**
   `FB_ST_TimerProbe.st`, включая объявления. Не использовать старый
   `FB_Room_N1` вместо проверяемого блока.
3. Выполнить штатную проверку/компиляцию. Записать версию Owen Logic, точную
   команду меню, полный текст диагностики и снимок окна. Ошибки исправлять
   в исходнике, а не только в несохранённом редакторе. Повторить компиляцию.
4. Вернуться в «Схема». Из «Функциональные блоки на ST» разместить один
   `FB_ST_TimerProbe`. Подключить тестовый I1 к ENABLE, DONE к Q1. Названия
   I1/Q1 относятся только к симулятору, электрические клеммы не назначены.
5. File → Save Project As: новое имя
   `Airlock_ST00_TIMER_GUI_<UTC>.owle`. В редакторе блока File → Export
   сохранить отдельный `.fbst`. Записать SHA256 обоих файлов и исходника.
6. Скомпилировать **целую схему** с размещённым и подключённым экземпляром,
   сохранить диагностику нулевых ошибок. Компиляция редактора блока и всей
   схемы — разные наблюдения, записать оба результата.
7. Запустить штатный Simulator. Сначала ENABLE=FALSE, DONE=FALSE. При переходе
   ENABLE=TRUE проверить DONE=FALSE до 10 s, затем TRUE. FRESH_RISE — один
   скан, RISE_COUNT увеличивается один раз. Длительное TRUE не добавляет фронтов.
8. ENABLE=FALSE должен сбросить DONE. После нового TRUE требуется полных 10 s.
   Повторить FALSE при 9.9 s и отсчитать новый полный интервал. Отдельно
   проверить запуск с ENABLE=TRUE: FRESH_RISE=FALSE, RISE_COUNT=0, пока LOW
   не был реально замечен. Записать, сбрасываются ли локальные переменные
   при перезапуске симулятора; пауза не равна холодному перезапуску.
9. Сохранить проект, закрыть **только этот тестовый процесс**, снова открыть
   сохранённую копию, повторить compile и короткую симуляцию. Зафиксировать
   реальный способ вызова SYS.TON, его единицы и сброс при FALSE.

Таймер должен вызываться циклически один раз за скан, в том числе при FALSE.
Пауза/F10 и режим непрерывного исполнения могут иметь разные часы: их
поведение нужно измерить, не считать число F10 равным миллисекундам.
Если нет точного управления границей 9.9/10 s, записать разрешение измерения
и оставить точную границу непроверенной. Один успешный Save As не даёт PASS.

## Этап A: собрать настоящий двухдверный проект

После этапа 0 создать новое имя проекта, не перезаписывая ST00. Добавить из
редактора `FB_Airlock2.st`. Разместить **один** экземпляр в графической схеме.
Обратные провода RS между графическими элементами не нужны: память находится
внутри ST. Вызов блока должен происходить каждый скан.

| Канал симулятора | Вход/выход блока | Смысл |
| --- | --- | --- |
| I1 | CLOSED_A | 1 = подтверждённо закрыта A |
| I2 | CLOSED_B | 1 = подтверждённо закрыта B |
| I3 | REQUEST_A | виртуальный запрос A |
| I4 | REQUEST_B | виртуальный запрос B |
| I5 | FIRE_NORMAL | 1 = нормальный режим |
| I6 | RESET | свежий ручной фронт восстановления |
| I7 | DATA_HEALTHY | виртуальная инъекция качества, не дополнительный полевой DI |
| Q1 | PERMIT_A | обычное тестовое разрешение A |
| Q2 | PERMIT_B | обычное тестовое разрешение B |
| Q3 | BUZZER | длительное открытие или защёлкнутая авария |
| Q4 | FAULT | отдельная тестовая диагностика |

READY, RESERVED_A/B, OVERTIME_A/B, EMERGENCY и STATE_CODE наблюдать в
ST-симуляторе/списке переменных. Это не дополнительные физические выходы.
Сохранить `Airlock_ST_2DOOR_GUI_<UTC>.owle` и `.fbst`, скомпилировать блок и
всю схему, записать нулевые ошибки, открыть сохранённую копию повторно.

Состояния: 0=HOLD, 10=READY, 20=GRANT_A, 21=OPEN_A, 30=GRANT_B,
31=OPEN_B, 90=INHIBITED. READY показывает завершение общей выдержки и
может оставаться TRUE во время неиспользованного разрешения. Он сам не
выдаёт PERMIT. В одном скане принимается только один переход состояния.

## Точный сценарий двух дверей

Вести журнал UTC/монотонного времени, входов, состояния и **обоих** разрешений.
Для каждого пункта указать ID исходной
[матрицы](CODEX-ST-NATIVE-QA-MATRIX.csv), фактическое наблюдение и файл доказательства.
Не переписывать NOT_TESTED в исходной матрице по результату Python/JS.

1. **2D01–02.** Холодный запуск с I1=I2=I5=I7=1, I3=I4=I6=0. Если запуск
   уже увидел FIRE_NORMAL/DATA_HEALTHY=0, сначала выполнить безопасный Reset
   и отсчитывать от него. До завершения 10 s оба PERMIT=0; затем READY=1,
   PERMIT всё ещё 0. Зафиксировать 9.0, 9.9 и первый скан после 10.0 s.
2. **2D03.** На паузе задать I3=I4=1 и выполнить **один** скан, проверив, что
   обе величины применяются до исполнения. Если GUI применяет значение
   сразу со сканом, использовать отдельный тестовый ST-стимулятор в GUI;
   последовательное переключение мышью не доказывает одновременность.
   До изменения герконов Q1=1, Q2=0, RESERVED_A=1.
3. **2D04.** Пока A зарезервирована, свежий I4 не даёт Q2. Удерживать I4
   через завершение A и выдержку: самопроизвольного разрешения нет. Нужны
   LOW-скан, затем новый HIGH. Повторить приоритет отдельно для запроса B.
4. **2D05.** Перезапустить с I3=1. Даже после 10 s Q1=0. Отпустить I3,
   выполнить скан, затем новый HIGH — только тогда возможно разрешение.
5. **2D06.** При закрытых герконах выдать свежий A, удерживать запрос.
   Q1 прекращается на первом скане с истёкшими 5 s, не позже 5 s + один
   измеренный цикл. Удержание HIGH не возобновляет Q1. После отмены без
   открытия новая 10 s выдержка не нужна; свежий B может получить разрешение.
6. **2D07.** При Q1=1 открыть A: Q1 сразу 0, RESERVED_A остаётся 1. Отпустить
   запрос, закрыть A: резерв снимается, начинается новая полная 10 s выдержка.
   До её завершения свежие запросы отклоняются и потребляются.
7. **2D08.** На 9.9 s выдержки открыть/закрыть любую дверь; после второго
   закрытия нужны заново полные 10 s. Незапрошенное одиночное открытие
   также должно сбрасывать общую выдержку.
8. **2D09.** Открытая A: до 30 s OVERTIME_A=0, затем 1 и BUZZER=1. Закрытие
   сбрасывает overtime/buzzer, если нет защёлкнутой аварии. Повторить для B.
9. **2D10–11.** Открыть обе: FAULT/BUZZER=1, оба PERMIT=0. Закрыть обе —
   авария сохраняется. Reset при открытой двери/активном запросе отклоняется.
   Закрыть двери, отпустить запросы, восстановить нормальные входы, сделать
   LOW→HIGH Reset. Нужны новая полная выдержка и свежий запрос.
10. **2D12.** Отдельно FIRE_NORMAL=0 и DATA_HEALTHY=0 во время разрешения:
    оба PERMIT сразу 0. Восстановление входов не снимает FAULT. Безопасный
    свежий Reset и новая 10 s выдержка обязательны. Аппаратная эвакуация
    этим тестом не проверяется.
11. **Дополнительные границы.** Открытие A одновременно с отпусканием I3;
    открытие в момент 5 s; отмена A одновременно со свежим B; новый запрос
    на скане окончания 10 s; Reset HIGH от запуска и через неисправность;
    авария и Reset в одном скане; холодный рестарт во время разрешения.
    Открытие владельца имеет приоритет над отпусканием/истечением; конкурент
    в скане отмены потребляется, два разрешения недопустимы всегда.

В `FB_Airlock2` таймер окна вызывается после перехода в GRANT, поэтому его
отсчёт начинается в скане принятия запроса. Его Q сразу снимает PERMIT;
RESERVED может сохраняться ещё один скан до обработки истечения автоматом.
При восстановлении вход таймера выдержки принудительно FALSE один скан,
отсчёт начинается следующим сканом. Эти особенности обязательно подтвердить
в Owen Logic.

## Отличия, найденные в прежнем эталоне

Исходный `ST_REFERENCE_VECTORS_OFFLINE.json` сохранён без изменений. Все его
11 двухдверных точек должны быть проверены отдельно. Семидверные 128 наборов
сохранены для следующего этапа; их наличие не означает реализации этапа B.

За пределами этих 11 точек старая FBD snapshot-модель снимает резерв при
одновременном открытии и отпускании запроса: unusedCancel видит прежнее
OPENED=FALSE. Новый ST сохраняет резерв до закрытия, как требует задание.
Старый таймер окна начинает отсчёт на следующем 20 ms модельном скане и
может держать разрешение до 5020 ms. В ST отсчёт начинается сразу в скане
принятия. Старый эталон не менять ради совпадения; расхождения проверить
и занести в нативный протокол.

## Шлюз к этапу B

Семидверную программу и новый OWLE создавать только после подтверждённых
ST00 и всех двухдверных проверок. Затем нужен настоящий GUI-шаблон
ПР102 + ПРМ-1 (либо согласованный ПР103 + ПРМ) и повторная компиляция.
Топология и арбитраж — из существующей CAD-фикстуры, шесть независимых групп,
без каскада по закрытым дверям. Бюджет с лампами — 16 DI/15 DO либо
22 DI/15 DO при двух локальных кнопках. BUSY=0. Изолированный наблюдаемый
K1 DI обязателен до открытия CNC-двери. Электрические клеммы и подключение
K1 этим пакетом не назначены.

Запрещены поиск/загрузка прибора, COM, Modbus, С2000-2, физические реле,
изменения VPN/действующих проектов, push/PR/merge/deploy без нового указания.
