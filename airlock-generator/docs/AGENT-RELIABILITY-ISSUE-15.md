# Issue #15 — надёжность read-only агента

Реализация расширяет `gateway/` существующего Airlock Generator. Программа ПР, генераторы ST/FBD, Owen Logic, СКУД, замки и пожарные цепи не изменяются. Разрешены только FC01/02/03/04. PR #13 / Issue #10 в эту ветку не включён.

## Опрос и границы времени

- Один незавершённый опрос на ПР. У каждого ПР собственные данные, срок годности, статистика и следующий срок запуска. После завершения выдерживается `pollMs`; пропущенные циклы отбрасываются. Общий цикл не ждёт зависший ПР. HTTP-сервер проверяет расписание каждые 100 мс; число ожидающих Promise не растёт с числом тиков.
- Чтения соседних адресов с одним FC объединяются. Данные одного ПР публикуются только после всех его пакетов и проверки всех назначенных сигналов. Ошибка последнего пакета отменяет и предыдущие. Бинарные сигналы принимают только 0/1; `State` — целое слово, неизвестные перечисления не дают READY.
- Возраст всей выборки отсчитывается **от начала опроса**, включая ожидание шины. Статистика `lastSuccessAt` отмечает завершение полного чтения. Возраст и расписание используют монотонные часы, даты в API — Unix milliseconds. Перевод системных часов не продлевает достоверность.
- Ошибка сразу очищает значения ПР; по истечении `staleMs` они также исключаются. Дверь не получает READY/GREEN без свежего Closed, BlockRequested, GreenPermit, FireNormal и READY всех участвующих управляемых комнат. Отсутствующий FireNormal представлен `fire: null`. ONLINE подтверждает только полную свежую выборку, не наличие процесса или открытого порта. Никакого физического разрешения на замок API не выдаёт.
- `pollBudgetMs` — общий бюджет чтения ПР (включая очередь), по умолчанию 10000 мс, допустимо 1000–60000. По превышении — `POLL_DEADLINE`, отмена транспорта и запрет принимать поздний результат. Если читатель не завершается даже после отмены, новый опрос того же ПР не запускается; другие ПР продолжают работать.
- TCP использует абсолютный таймер запроса `timeoutMs`, а не таймер бездействия: поступление отдельных байтов его не продлевает. Буфер ограничен 266 байтами, проверяются MBAP, transaction/unit/function и размер payload. Каждый запрос закрывает свой сокет.

## Одна шина — один мастер

Для COM-порта (без учёта регистра в Windows) или точного Linux tty-пути есть один владелец транспорта. Разные Unit ID делят FIFO: один активный запрос и **не более 16 ожидающих**, время ожидания не более 15000 мс; общий бюджет ПР может отменить его раньше. Последующие пакеты каждого ПР встают в хвост, поэтому ПР с большой картой не занимает шину монопольно. Разные порты и TCP независимы.

При зависании Python watchdog посылает TERM, через 200 мс KILL. **Порт освобождается только после события завершения процесса**. Если ОС не подтверждает завершение, шина остаётся изолированной; ожидающие запросы истекают, данные UNKNOWN. Запуск второго мастера для обхода зависшего процесса запрещён. Это намеренный выбор достоверности в пользу отказа, даже если требуется вмешательство оператора.

Python дополнительно держит неблокирующую межпроцессную блокировку в системном temp-каталоге; имя файла — SHA256 имени порта. Блокировка освобождается ОС при смерти процесса; файл не удаляется (удаление создало бы гонку разных inode). На Linux используется flock, на Windows — msvcrt.locking. Сам pymodbus 3.15 открывает pyserial с `exclusive=True`. Эта защита распространяется на cooperating helpers и права эксклюзивного открытия ОС; не заменяет запрет подключать другой физический master. На Linux не используйте альтернативные symlink-пути к той же шине: профиль принимает только `/dev/ttyUSBn`, `/dev/ttyACMn`, `/dev/ttySn`.

Настройки baud/parity/stopbits/режим на одной шине должны совпадать; повтор Unit ID и неверное соответствие имени `PLC_<id>` контроллеру отвергаются при загрузке профиля. Каждый экземпляр агента должен использовать свою локальную конфигурацию; второй агент на занятой шине получает BUS_BUSY, не ONLINE.

## Persistent и сохранённый one-shot

Существующий `rtuMode: "oneshot"` остаётся режимом по умолчанию. Отсутствующее поле означает one-shot. На каждый пакет создаётся Python и заново открывается serial; проще жизненный цикл, выше накладные расходы запуска и инициализации.

Для **всех ПР одной шины** можно явно задать в локальном JSON:

```json
{"rtuMode": "persistent"}
```

Это поле добавляется к существующему объекту контроллера вместе с подтверждёнными параметрами порта, не является самостоятельным профилем. Persistent держит один Python/client на шину, последовательный протокол JSONL с ID запроса и сбросом старого входного буфера перед чтением. После ошибки client закрывается; следующий запрос создаёт новый. После краха helper следующий запрос создаёт новый процесс только после подтверждённого завершения предыдущего. Таймауты Unit ID могут различаться. Никаких автоматических повторов чтения (`retries=0`), автоматического переключения режима или обнаружения портов нет. После 10 с простоя helper закрывается; запуск происходит только при запросе.

Компромисс: persistent уменьшает число процессов и повторных открытий (автотест: 10 Unit ID — один helper), но удерживает порт и память интерпретатора. До 16 ПР/256 bindings; в худшем случае по отдельному процессу на независимую активную шину. Не заявляем измеренное ускорение реального USB-адаптера. Для большой карты/медленной шины подберите подтверждённые pollBudgetMs/staleMs: если выборка заняла больше staleMs, даже успешное завершение остаётся STALE. Увеличение срока годности требует отдельного обоснования на стенде. Откат: остановить агент, вернуть oneshot у всех ПР шины и запустить вручную.

## Локальные профили и приватность

Сохраняется версия `airlock-scada-connection/1`; новые поля необязательны. Неизвестная версия, неверные интервалы/FC/адреса и несовместимые настройки шины отвергаются **до подключения**. Профиль не может содержать поля password/token/secret/credential, в том числе внутри модели.

Храните реальные JSON только вне checkout или в игнорируемом `airlock-generator/.local/`. Не добавляйте их, backups и журналы в Git/PR. Это локальные файлы, без шифрования; Windows ACL задаёт владелец ПК. Linux atomic writer создаёт файл с mode 0600. Файлы, ранее сохранённые браузером, имеют права каталога загрузок.

```text
node gateway/profile-store.js save <local-target.json> <local-source.json>
node gateway/profile-store.js restore <local-target.json>
node gateway/preflight.js --config <local-target.json>
```

Сначала полностью валидируется новый профиль; предыдущий валидный профиль сохраняется через temp+fsync+rename в `.bak`, затем так же заменяется основной файл. Восстановление читает и валидирует `.bak`, атомарно заменяет основной, сохраняя backup. Ошибка JSON/валидации не изменяет файлы. После неудачного rename остаётся предыдущий валидный основной файл и backup, временный файл удаляется. Нет HTTP API записи/restore и live reload; для применения нужен ручной перезапуск. Операции с одним профилем выполняйте последовательно одним оператором. Это не менеджер секретов.

`/api/project` отдаёт модель и bindings, но только id/model/protocol/redacted у ПР: IP/host, TCP port, COM, baud/parity/stopbits, Unit ID и timeout в браузер не попадают. Из-за этого экспорт скрытого рабочего профиля в UI отключён; исходный локальный JSON редактируется на ПК агента. Ошибки библиотеки/процесса не передаются в браузер или журнал: используются фиксированные причины отказа и числовой `MODBUS_EXCEPTION_n`.

`GET /api/status`: lastPollAt, lastSuccessAt, sampleAt, durationMs, consecutiveFailures, totalFailures, dataAgeMs, offlineCause и polling по ПР; число активных/ожидающих запросов. `GET /api/events`: последние 50 записей; RAM до 500, JSONL по умолчанию до 5 MiB + 3 архива, запись на диск только с AIRLOCK_EVENT_LOG. Смена причины OFFLINE также фиксируется; восстановление задаёт новую базу DI/Q без ложного SIGNAL_CHANGED. Ошибка диска сохраняет bounded RAM и выдаёт `journal.error: JOURNAL_IO`, не останавливает опрос/HTTP и не публикует путь файла.

## Автономные проверки

Полный обязательный набор без установки Modbus-зависимостей:

```bash

```

Новые тесты: `agent-reliability.test.js` (виртуальное время, 30 пропущенных циклов, поздний ответ, GREEN, age и перевод часов), `rtu-supervisor.test.js` (ограниченная очередь, TERM/KILL/close, FIFO, другие шины), `tcp-faults.test.js` (только fake loopback responder, потерянные/медленные байты, exceptions/refusal/reconnect, параллельные ПР, отказ позднего пакета), `rtu-worker-faults.py` (настоящие helper-процессы с fake pymodbus, блокировка между процессами, hard kill), `profile-store.test.js` (атомарная замена и инъекция ошибки rename). Расширены существующие HTTP/journal/health тесты.

Настоящий RTU parser проверяется отдельно, без оборудования и без открытия serial:

```bash
python -m venv <test-venv>
# Запустить Python из этого venv:
python -m pip install -r tests/requirements-rtu.txt
python -B tests/rtu-library-faults.py
```

В этом тесте `serial.serial_for_url` заменяется адаптером в памяти, реальный pymodbus формирует/проверяет FC01–04/CRC/Unit ID; проверяются повреждение CRC, потеря байта, молчание, неверный FC/Unit, exception, unplug/replug. Нет fallback к настоящему COM. CI запускает этот тест и offline smoke на ubuntu-latest и windows-latest (Node 22, Python 3.13).

На HOME-PC/Z4559 доступен **только ручной offline smoke**, без старта агента и автозапуска:

```powershell
.\scripts\windows\test-telemetry-offline.ps1
# С заранее подготовленным тестовым venv, по желанию:
.\scripts\windows\test-telemetry-offline.ps1 -PythonPath <venv-python.exe> -RealLibrary
```

Первый Windows CI выявил гонку cleanup fake TCP responder: listener уже закрыт, а accepted sockets ещё не доставили close. Fixture исправлен ожиданием close каждого сокета; проверка нулевого числа активных соединений сохранена. Это исправление тестового жизненного цикла, без ослабления проверок телеметрии.

Наблюдалось в Cloud Linux: полный codex-check PASS, headless MODEL 8/8; отдельный real pymodbus 3.15.0 / pyserial 3.5 memory-serial PASS. Node 24.19.0, Python 3.12.14. Windows/HOME-PC/Z4559 и физический ПР в этой сессии **не проверялись**. Автотесты подтверждают свойства программы в указанных моделях отказов; физическая совместимость, задержки USB/RS485 и электрическая безопасность из них не следуют.

## Отдельная физическая PR100-проверка (ещё НЕ выполнена)

1. Только отдельный экспериментальный ПР и адаптер, без замков/исполнительных нагрузок и действующей шины СКУД. Существующие программы и оборудование не изменять. Остановить другие мастеры именно экспериментальной шины; не останавливать действующий skud-kpp2. Подтвердить схему по документации прибора и адаптера.
2. Определить актуальный COM в диспетчере устройств вручную. Проверить baud/parity/stopbits, уникальные Unit ID и документированную карту чтения для каждого ПР. Не использовать исторические значения как подтверждение этого прибора. Никаких upload, FC05/06/15/16/23, broadcast или перебора адресов.
3. Сохранить локальный профиль только с подтверждёнными FC01–04 bindings; сначала oneshot. Выполнить preflight (он не открывает порт), затем вручную `node gateway/server.js --config <local-profile.json>`. Автозапуск остаётся opt-in; новый scheduled task не устанавливать без отдельного разрешения.
4. Наблюдать 60 циклов: сопоставить DI/Q с индикацией прибора без изменения входов/программы; записать durationMs, dataAgeMs, lastSuccessAt, failures и число pending. Только DI/Q не подтверждают GREEN; неназначенные критические сигналы UNKNOWN.
5. На экспериментальном стенде отсоединить связь одного ПР (не питание действующей системы). Подтвердить его OFFLINE/UNKNOWN не позже timeout/budget или staleMs, отсутствие роста очереди, продолжение опроса другого ПР; сравнить длительность круга одной шины и независимого TCP/другой шины. Точные задержки зафиксировать как **измеренные**, не расчётные.
6. Вернуть связь; ONLINE допускается только после новой полной выборки. Повторить с отсоединением/возвращением USB-адаптера, убедиться, что порт после replug не сменился; если сменился — остановить агент и исправить профиль вручную. Не включать автоматический COM discovery.
7. Остановить агент, включить persistent у всех ПР шины и повторить шаги 4–6. Сравнить измеренные время/нагрузку/стабильность; при регрессии вручную вернуть oneshot. Одновременный запуск двух режимов на одном порту запрещён.
8. Итоговый приватный протокол: идентификатор тестового оборудования и версии ПО, подтверждённая карта, режим, измерения, ожидаемые и наблюдавшиеся состояния отдельно, список NOT_TESTED/FAIL. Не публиковать реальные COM/IP/пароли. RTU_LINK_PASS/IO_READ_PASS/FAULT_RECOVERY_PASS/SCADA_LIVE_PASS ставятся только по наблюдениям. Это не допуск управления замками/эвакуацией.
