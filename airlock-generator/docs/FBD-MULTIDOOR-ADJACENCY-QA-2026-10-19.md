# Airlock Generator — проверка нескольких дверей и смежных помещений (19.10.2026)

**Статус:** `FBD_MULTIDOOR_ADJACENCY_OFFLINE_PASS` после успешного запуска
`node tests/fbd-multidoor-adjacency.test.js` на HOME-PC. Область проверки:
**JS-граф FBD, генерируемые ST-интерфейсы, автономная модель помещений**.
Это не native-компиляция Owen Logic и не аппаратное испытание.

## Покрытие

Файл `tests/fbd-multidoor-adjacency.test.js` создаёт тестовые схемы:

1. Центр H с 2, 3, 4 и **5 отдельными дверями**. За каждой дверью
   находится соседняя комната L1–L5. У каждой соседней комнаты есть
   второй выход в неконтролируемый коридор X.
2. **Пять последовательных помещений** A—B—C—D—E. Каждая комната
   имеет отдельный выход в X: девять дверей, пять отдельных FB.
3. Замкнутая схема **четырёх помещений A–B–C–D–A** с отдельными
   выходами. Восьми дверям назначены три логических контроллера.
4. **Две разные двери AB1 и AB2** между одними и теми же помещениями,
   плюс внешние выходы AX, BX.

Двенадцать проверок охватывают:

- Для каждого управляемого помещения количество `I_D_*_Closed`,
  `O_D_*_Block` и `O_D_*_Overtime` совпадает с числом его дверей.
- На каждой физической двери **ровно один исходный геркон**.
  Для общей двери один квалифицированный сигнал поступает в два FB.
- **FINAL_BLOCK** для общей двери получает **два независимых запроса**,
  объединённых OR. Для выхода в неконтролируемый коридор — один.
- GREEN проверяет участвующие помещения; никакой вычисленный GREEN
  не является аппаратной командой питания замка.
- При открытии HL1 центр H запрещает другие входы HL2–HL5. Сосед
  L1 запрещает свой внешний выход L1X. Выходы других соседей L2X–L5X
  остаются разрешёнными, если их местные условия удовлетворены.
- У соседней комнаты с режимом `mutual` блокировка снимается сразу
  после закрытия. У центра `purge` действует полный интервал.
  Повторное открытие в продувке перезапускает отсчёт.
- Два одновременно открытых входа центра вызывают фиксируемую
  неисправность, запрещающую GREEN.
- Открытие BC в цепочке влияет на B и C, но не переводит
  несмежные A, D, E в состояние занятого шлюза.
- Разные герконы двух параллельных дверей AB1/AB2 не объединяются.
- При `FireNormal=false` программные запросы блокировки сбрасываются,
  но GREEN остаётся запрещённым.
- Попытка создать управляемую комнату с единственной дверью
  отклоняется, а не превращается в незавершённую ST-схему.

## Контроллеры и ограничения

Для синтетического центра используется **только программная модель**
PR103, конфигурация `32 DI / 32 DO` как тестовая оценка достаточности
ресурсов, **не подтверждённое физическое исполнение оборудования**.

Четырёхкомнатный пример проверен также в варианте трёх ПР:
пересылка входов и выходов представлена логическими `REMOTE`-узлами.
Сигналы сети не прошли аппаратную настройку Modbus/TCP.

**Важная граница модели:** открытия двери в B или C сами по себе
не означают автоматически глобальную блокировку всех *последующих*
комнат. Действует правило для дверей **непосредственно участвующих
помещений**, с учетом их независимых блокировок. Транзитивная
блокировка по всей цепочке — это **другая политика**, которая сейчас
не реализована в генераторе. Поля `rules` и `exemptions` отклоняются
вместо молчаливого игнорирования. Запрос на каскад следует оформить
отдельным набором точных правил и тестов.

Остаются незавершёнными: **полная native генерация .owle**,
нативная проверка Owen Logic для произвольной схемы, назначение
физических клемм, восстановление после пожарного сигнала,
диагностика обрыва геркона, аппаратная электробезопасность и
независимая проверка аварийного выхода.

## Воспроизведение

Запускать из папки `airlock-generator`:

```bash
node tests/fbd-multidoor-adjacency.test.js
npm run check
```

Новый тест добавлен в `npm run test:fbd` и тем самым
в полный `npm run check`. Не обращается к COM5, ПР100, СКУД,
реальным входам/выходам или исполнительным устройствам.
