# Issue #10 — генерация полной логической FBD-карты

Генератор собирает общий типизированный граф из существующих `st-generator.js`,
`project-wiring.js`, `hardware-planner.js` и `distributed-planner.js`.
Логика помещений не переписана: экспортируются те же ST-блоки, а автономные
проверки используют `st-testbench.js`.

Статусы новой схемы: **FBD_PLAN_PASS** после проверки инвариантов;
**NEEDS_NATIVE_GUI / NEEDS_OWEN_VALIDATION** для native-сборки;
**PHYSICAL_PASS: NOT_TESTED**. Генерация готового `.owle` не заявляется.
Исторические QA-OL-006 и QA-OL-012 A–F приняты для старой тестовой схемы,
см. [PR #6](https://github.com/4qsn1k/4qsn1k.github.io/pull/6).
Они не повторялись и не подтверждают новый произвольный граф.

## Использование

В конструкторе выберите оборудование и владельцев помещений/герконов/выходов
в существующих панелях. В панели «Полная схема FBD» можно проверить план,
скачать JSON, матрицу связей CSV и сценарии испытаний новой схемы.
Демонстрационный ПР100 с восемью DO недостаточен для исходной схемы:
нужна подходящая конфигурация, а не обход проверки ресурсов.
Каждая кнопка экспорта заново проверяет текущую модель.

Из `airlock-generator/`:

```bash
node scripts/export-fbd-plan.js experimental/fixtures/fbd-four-rooms.model.json /tmp/airlock-fbd-example
npm run test:fbd
bash scripts/codex-check.sh
```

Выходной каталог должен быть новым: существующие файлы не перезаписываются.
Пример содержит четыре активных помещения, восемь дверей и три ПР.
Создаются `fbd-plan.json`, `connection-matrix.csv`, ST-файлы,
`native-test-plan.md`, `native-evidence.json` и `sha256.json`.
Повторный запуск в другой новый каталог даёт те же байты.
CLI также принимает существующий пакет `airlock-scada-project/1`.
Никакие адреса, COM-порты или токены не нужны.

## Граф и распределение

- Одна исходная DI-запись на контролируемую физическую дверь. Один квалифицированный
  сигнал CLOSED разветвляется на все связанные FB и расчёт зелёного.
- Запросы каждого связанного помещения объединяются OR. GREEN требует закрытия,
  нормального пожарного входа, исправности питания/датчика, отсутствия итогового
  запрета, READY, отсутствия Fault/Fire и подтверждения данных всех помещений.
- У каждого ПР с FB резервируются локальные FireNormal/ResetFault;
  ПР только с дверными выходами нужен FireNormal, без лишнего ResetFault.
  Проверяется ёмкость каждого ПР, включая ПРМ.
  ПР с выходом двери может не содержать ни одного FB помещения.
- Межконтроллерные сигналы проходят только через явные REMOTE-узлы.
  В существующей карте размещения сохранены прежние `consumers`;
  `typedConsumers` содержит реальные ID портов новой схемы.
- BASE/PRM — предварительные слоты. `terminal: null`,
  `mappingStatus: UNASSIGNED`, `modbusAddress: null` сохраняются даже при
  наличии пользовательской ссылки на геркон. Это не назначение заводских клемм.
- Отдельный SPDT-выход на пару ламп: NC красный / NO зелёный.
  `FINAL_BLOCK` — логический запрос, `GREEN_PERMIT` — индикация разрешения,
  `lockCommand: null`. Утрата питания ламп может погасить оба цвета.

ID портов кодируются парой `[nodeID, portName]`; порядок детерминирован.
Проверяются уникальность ID, типы BOOL/UDINT, направление и единственный
источник каждого входа, отсутствие висячих проводов/циклов, происхождение
входов GREEN и полного набора независимых запросов блокировки.
Выходы диагностики FB, не используемые внутри FBD, остаются наблюдаемыми портами.

## Недостоверные данные и восстановление

`fbd-evaluator.js` — автономный оценщик графа, не ещё один автомат помещений.
Для выходов ROOM_FB он принимает наблюдаемые результаты существующей модели
или штатного симулятора. Образец сигнала:

```js
{value: true, valid: true, atMs: 100}
```

`nowMs` и `atMs` задаются по монотонным часам тестового приёмника.
Тайм-аут 100..600000 мс выбирается явно; допустимый диапазон не означает
утверждения какого-либо значения для объекта. BOOL не приводится из строк/чисел.
Нет сигнала, ложное качество, истёкший срок, время из будущего, неизвестные
питание/здоровье датчика или потерянный remote-сигнал исключают зелёный.
`SENSOR_OK` требует отдельного подтверждённого источника; один геркон
не позволяет определить обрыв или застрявший контакт.

Существующий `network-watchdog.js` проверяет последовательность и время каждого
канала. Replay и повреждённый известный кадр немедленно отзывают свежесть;
корректный новый кадр может восстановить свежесть канала. Это не транспорт Modbus.
Оценщик сверяет также качество и согласованность источника с принятой копией;
это глобально наблюдаемая offline-модель, не готовый распределённый протокол.

`AirlockFbdEvaluator.evaluate(plan, options)` сравнивает один снимок.
Для последовательностей используйте `AirlockFbdEvaluator.create(plan)` и его
`evaluate(options)`: после наблюдённого пожара, fault, потери питания/датчика
или потери качества ранее подтверждённых данных разрешение зависимых дверей
остаётся снятым со статусом `UNRESOLVED_RECOVERY_POLICY` даже после восстановления
данных. Независимые двери не получают чужую аварию. Сброса этой отметки нет:
его нельзя придумывать до утверждения политики восстановления. Новая сессия
создаёт отдельный автономный эксперимент, а не команду перезапуска оборудования.
Неизвестный итоговый запрет остаётся `null`; физическое действие не выбирается.

## Native-граница и следующие действия

PR #17 добавил обезличенное подтверждение структуры native-портов, OR и
16 соединений. Старый полный образец ST-экземпляров подтверждает имена/типы
интерфейсов. В Issue #14 они используются вместе для строгого сопоставления
с существующим графом; см. [OWLE-NATIVE-SERIALIZATION-ISSUE-14.md](OWLE-NATIVE-SERIALIZATION-ISSUE-14.md).
BOOL в метаданных FBD имеет код 0, а в старом ST-архиве — код 6;
эти пространства не смешиваются.

Полных метаданных проекта, геометрии, связей определений/экземпляров и native
шаблонов качества/GREEN/remote пока нет. `nativeDocument: null`,
`usableForSerialization: false` обязательны; `.owle` не создаётся. Точный
запрос дополнительных TEST-образцов и новая процедура HOME-PC описаны в
руководстве Issue #14. Старая native QA не подтверждает новый выход генератора.
Сетевая сериализация, политика перезапуска, электрические уровни, аппаратная
эвакуация, настоящие клеммы и регистры требуют отдельного проектирования.
Доступ к HOME-PC/Z4559 или программирование ПР этим изменением не запрашивается.

Сохранены ограничения существующих компонентов: 2..24 двери на активное
помещение, до 17 ПР в плане оборудования; ID помещений — ASCII буквы/цифры/`_`.
Некорректные ID, повторные герконы, коллизии ST-имён, отсутствующие помещения,
неизвестные режимы, направленные правила и исключения, не поддерживаемые
текущим ST, отклоняются явно. Неограниченный native-проект не заявляется.

## Проверки и артефакты

Новые проверки включены в `npm test` и полный `scripts/codex-check.sh`:
9 групп генератора, 12 групп оценщика (256 комбинаций GREEN и 36 графов
с фиксированным seed), 4 группы CLI/артефактов. Это программные тесты.
GitHub Actions сохраняет полный `qa-reports/codex-check.log`, отчёт оценщика
и экспорт четырёх помещений с SHA256 в артефакте `airlock-full-offline-qa`.

Опционально, при доступных Playwright и Chromium, запустите локальный сервер
`python3 -m http.server 8000 --bind 127.0.0.1 --directory /workspace/4qsn1k.github.io`,
затем `node tests/fbd-browser-smoke.js`. Проверяются реальные скачивания JSON/CSV/QA,
отказ при недостаточных ресурсах/ошибочной текущей модели и совместимость
экспорта SCADA. Browser-проверка не входит в dependency-free CI.

В ходе проверки SCADA обнаружены и исправлены два прежних дефекта экспорта:
проверка top-level `const` через свойство `window` и литеральный `\\n` после JSON.
В `tests/hmi.test.js` добавлена проверка фактического portable-экспорта.
